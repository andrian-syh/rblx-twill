# Twill documentation site

The documentation site for Twill, built with [Astro](https://astro.build) and
[Starlight](https://starlight.astro.build).

## Commands

| Command | Action |
| --- | --- |
| `npm install` | Install dependencies |
| `npm run dev` | Dev server at `localhost:4321` |
| `npm run build` | Build to `./dist/` and validate every internal link |
| `npm run preview` | Preview the build locally |

## Layout

```
src/content/docs/
├── index.mdx          landing page
├── getting-started/   what it is, installing, first run
├── core-guides/       the concepts every project needs
├── guides/            how do I, plus tips and best practices
├── reference/         the API, plus project reference
└── explanation/       why it works this way
```

Sidebar order is set explicitly in `astro.config.mjs`, not autogenerated. An
entry naming a page that does not exist fails the build.

## Before writing a page

Read [STYLE.md](./STYLE.md). It covers the house voice, what is banned, and why
every link has to be root-relative.

## Before changing how it looks

Read [DESIGN-DARK.md](./DESIGN-DARK.md) (the Factory specification for dark theme) and [DESIGN-LIGHT.md](./DESIGN-LIGHT.md) (the clean monochromatic specification for light theme).
`src/styles/custom.css` maps its tokens onto Starlight's, and the site is dark
only by decision, so there is no theme selector.

Code blocks are the one surface the design system stops at. They are left close
to how Expressive Code ships them, because styling the frame from `custom.css`
cost the copy button and the file-name tab their shape.

## Search does not work in `astro dev`

Starlight's search is Pagefind, and Pagefind indexes the **built** HTML. There is
no index during development, so the dialog opens and finds nothing. That is
expected, not a fault.

To test search:

```sh
npm run build && npm run preview
```

## When the dev server disagrees with a build

`astro dev` keeps state in `.astro/` and `node_modules/.vite/`, and a restart does
not clear either. After changing `astro.config.mjs` the dev server can keep serving
the previous configuration's output, including asset URLs that no longer exist and
now 404. A build is unaffected, so the two disagree and the dev server is the one
that is wrong.

If something renders correctly in `npm run build` but not at `localhost:4321`:

```sh
npx astro dev stop
rm -rf .astro node_modules/.vite
npx astro dev
```

Check a build before concluding that a dev-only symptom is a real bug.

**Stop the dev server before clearing `.astro/`, and before any build that clears
it.** The content collection index lives there. Deleting it under a running dev
server empties that index, and the next request fails with `AstroUserError: The
slug "..." specified in the Starlight sidebar config does not exist` for a page
whose file is sitting right there on disk. The file is fine; the index is gone.
Restarting the dev server rebuilds it.

## Testing the project-page sub-path

The deployed site is a GitHub project page, so it is served under
`/rblx-twill`. The Pages workflow supplies that as `BASE_PATH`; locally `base`
stays `/` so `npm run dev` serves from the root. To check the sub-path build:

```sh
MSYS_NO_PATHCONV=1 BASE_PATH=/rblx-twill npm run build && npm run preview
```

`MSYS_NO_PATHCONV=1` is only needed in Git Bash, which otherwise rewrites
`/rblx-twill` into a Windows path and produces hrefs like
`/C:/Program Files/Git/rblx-twill/news/`. In PowerShell use `$env:BASE_PATH = '/rblx-twill'`.

The workflow in `.github/workflows/deploy.yml` runs the same build on every push
to `main` that touches `site/`, and the link validator fails the deploy rather
than shipping a broken link. Run this locally when you have changed anything that
emits a URL outside Markdown, such as a component or a frontmatter link.
